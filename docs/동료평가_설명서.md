## ⚠️ 먼저 — 이 미션의 가장 큰 위험

**실제 API 호출을 한 번도 한 적이 없습니다.** 테스트 42개는 전부 가짜 응답으로 돌고,
README의 출력 예시는 🔄 표시가 붙은 **형식 예시**입니다.

평가자가 **"지금 돌려보세요"** 라고 하면 `ANTHROPIC_API_KEY`가 환경변수에 있어야 합니다.
없으면 그 자리에서 실행이 안 됩니다.

**평가 전에 반드시 하셔야 할 것** (하은님 몫, 저는 키를 다룰 수 없습니다)

```bash
# 키가 환경변수에 들어있는지 확인 — 아래가 비어 있으면 안 됩니다
echo "${ANTHROPIC_API_KEY:0:10}..."

# 비어 있으면 (키 값은 직접 입력하세요)
export ANTHROPIC_API_KEY="sk-ant-..."
```

그리고 **평가 전에 한 번은 실제로 돌려보세요.** `commit` 한 번이면 1센트도 안 됩니다
(입력 2,400토큰 / 출력 110토큰 기준 약 $0.002). 그 출력을 README의 🔄 자리에 넣으면
"실측입니다"라고 말할 수 있습니다.

**만약 키가 없는 상태로 평가를 받게 되면** — 숨기지 말고 이렇게 말하는 게 낫습니다.

> "실제 호출은 API 키가 필요해서 지금 환경에 없습니다. 대신 **`preview` 명령으로
> API에 무엇을 보내는지 전부 보여드릴 수 있고**, 테스트 42개로 검증·재생성·후처리가
> 맞물려 도는 걸 확인하실 수 있습니다. 호출 직전까지의 모든 단계가 이 두 가지로 증명됩니다."

`preview`는 **돈이 들지 않는데 프롬프트 전체를 보여줍니다.** 이 미션의 핵심이
"어떤 입력을 주는가"라서, 사실 `preview`가 가장 설명력 있는 시연입니다.

## 1. 30초 요약 — "무엇을 만들었나"

> **"`git status`와 `git diff`를 읽어서, 커밋 메시지와 Pull Request 초안을
> AI에게 쓰게 하는 터미널 도구입니다.**
>
> 명령은 세 개입니다. `commit`은 커밋 메시지를, `pr`은 PR 제목과 본문을 만듭니다.
> **`preview`는 API를 부르지 않고 '무엇을 보낼지'만 보여줍니다** — 돈이 들지 않습니다.
>
> 핵심은 단순히 API를 부르는 게 아니라 **세 가지**입니다.
> 첫째, **보내기 전에 민감정보를 가립니다.** `git diff`에는 `.env` 수정이나
> 하드코딩된 키가 그대로 들어있을 수 있고, **외부로 한 번 보내면 되돌릴 수 없습니다.**
> 둘째, **돌아온 결과가 형식 규칙을 지키는지 검증하고**, 틀리면 무엇이 틀렸는지
> 알려주며 딱 한 번 다시 시킵니다.
> 셋째, **생성된 문구는 초안이고 적용은 사람이 판단합니다.** 자동으로 커밋하거나
> push하지 않습니다."

## 2. 요구사항 1 — Git 변경 사항 수집

### ① 평가자가 확인하는 것
`git status`와 `git diff` 결과를 프로그램 입력으로 연결했는지.

### ② 실행할 명령
```bash
python3 main.py preview
sed -n '1,45p' aigitgen/gitctl.py      # subprocess 로 git 을 실행하는 부분
```

### ③ 나올 결과
```
[INFO] Git status 수집 완료: 1개 파일 변경 감지 (staged)
[INFO] Git diff 수집 완료: 11줄
```

### ④ 읽을 말

> "git을 다루는 방법은 두 가지가 있었습니다. **GitPython 같은 라이브러리를 쓰는 것**과
> **`subprocess`로 git 명령을 직접 실행하는 것**입니다. **`subprocess`를 골랐습니다.**
>
> 이유는, 이 과제가 설명하라고 요구하는 게 바로 **'git 명령 실행 결과를 프로그램 입력으로
> 연결하는 방식'** 이기 때문입니다. 라이브러리를 쓰면 그 연결 지점이 라이브러리 안으로
> 숨습니다. `subprocess`로 하면 **코드에 `git status --short`라는 글자가 그대로 보입니다.**"

`subprocess`를 모르시는 평가자가 있을 수 있으니 한 줄 풀이도 준비해 두세요.

> "`subprocess`는 **파이썬이 터미널 명령을 대신 실행하고 그 출력을 문자열로 받아오는**
> 기능입니다. 제가 터미널에 `git status`를 치는 것과 똑같은 일을 파이썬이 하는 겁니다."

**두 가지 옵션을 왜 줬는지** (`_run` 함수의 인자)

> "`text=True`는 결과를 바이트가 아니라 **문자열로 받으려고** 쓴 겁니다.
> `errors="replace"`는 **diff 안에 UTF-8이 아닌 바이트가 섞여도 프로그램이 죽지 않게**
> 하려고 넣었습니다. 이미지 같은 바이너리 파일을 수정하면 실제로 그런 바이트가 들어옵니다."

### 설명하기 좋은 판단 세 가지

**(1) staged / unstaged 자동 판단**

> "`--staged`나 `--unstaged`를 주지 않으면 **자동으로 판단합니다.** staged에 변경이 있으면
> 그쪽을 보고, 없으면 unstaged를 봅니다.
>
> 왜냐면 이건 **커밋 메시지를 뽑는 도구**입니다. '이제 커밋할 것'은 staged에 있습니다.
> 그래서 staged가 있으면 그걸 우선하는 게 사용자가 기대하는 동작입니다."

**(2) untracked 파일을 목록에는 넣는다**

> "`git diff`는 **아직 git이 추적하지 않는 새 파일의 내용을 보여주지 않습니다.**
> 그런데 '무엇이 바뀌었나'를 정확히 말하려면 그 파일이 생겼다는 사실은 알려야 합니다.
> 그래서 `git ls-files --others`로 목록에만 추가합니다."

**(3) diff가 비면 API를 부르지 않고 멈춘다 — 여기가 제일 중요합니다**

`main.py` 178~187줄입니다.

> "**새 파일만 있으면 파일 목록은 1개인데 diff는 0줄입니다.** 이 상태로 API를 보내면
> 모델은 '무엇이 바뀌었는지' 전혀 모르는 채로 커밋 메시지를 써야 합니다.
> **돈은 쓰면서 근거 없는 메시지가 나옵니다.** 그게 이 도구에서 제일 위험한 실패입니다.
>
> 그래서 여기서 멈추고 `git add`를 안내합니다. **API를 호출하지 않았다고 명시적으로
> 출력합니다** — 사용자가 돈이 나갔는지 궁금해하지 않게요."

```
[WARN] 변경된 파일은 있지만 diff 가 비어 있습니다. 추적되지 않은 새 파일(untracked)뿐인 것 같습니다.
[INFO] `git add <파일>` 로 스테이징한 뒤 다시 실행하세요. API 를 호출하지 않았습니다.
```

### 오류 처리 — 실측했습니다

```bash
cd /tmp && python3 ~/Desktop/Codyssey/본과정/ai-gitgen/main.py commit
```

> "git 저장소가 아닌 곳에서 실행하면 **종료코드 1**로 끝나면서 이렇게 안내합니다.
> `git`이 설치조차 안 돼 있는 경우(`FileNotFoundError`)도 따로 잡아서 다른 메시지를 냅니다.
> 둘을 같은 메시지로 묶으면 사용자가 무엇을 고쳐야 하는지 모릅니다."

## 3. 요구사항 2 — AI API 연동 (요청 구성 / 응답 처리 / 예외 대응)

### ① 평가자가 확인하는 것
API 요청을 어떻게 구성하고, 응답을 어떻게 처리하고, 실패를 어떻게 다루는지.
그리고 **모델·토큰·파라미터를 CLI 옵션으로 바꿀 수 있는지.**

### ② 실행할 명령
```bash
python3 main.py commit --help          # 옵션 전체
sed -n '124,146p' aigitgen/llm.py      # 요청 조립 (_build_kwargs)
sed -n '172,215p' aigitgen/llm.py      # 예외 처리 7단
```

### ③ 나올 결과
`--model`, `--max-tokens`, `--effort`, `--temperature` 가 `API 파라미터` 그룹으로 묶여 나옵니다.

### ④ 읽을 말 — 요청 구성

> "요청에 들어가는 건 네 가지입니다. **`model`**(어느 모델), **`max_tokens`**(출력 길이 상한),
> **`system`**(역할과 규칙), **`messages`**(실제 변경 사항)입니다.
>
> **`system`과 `messages`를 나눈 게 중요합니다.** `system`에는 **매 호출마다 똑같은**
> 역할·규칙을 넣고, `messages`에는 **매번 달라지는** diff를 넣습니다. 이유는 두 가지입니다.
> 하나는 **규칙이 데이터에 섞여 희석되지 않게** 하는 것이고, 하나는 **같은 내용은 캐시가
> 되기 때문**입니다."

### ④ 읽을 말 — `temperature` 이야기 (이게 이 미션의 '발견'입니다)

**여기가 가장 설명하기 좋은 부분입니다.** 과제가 요구한 것과 현실이 달랐고, 그걸 어떻게
처리했는지를 보여줄 수 있습니다.

> "과제는 `temperature`를 CLI 옵션으로 제공하라고 요구합니다. 그런데 만들면서 확인해보니
> **지금 쓰는 Claude 모델들은 `temperature`를 보내면 400 에러를 돌려줍니다.**
> 샘플링 파라미터가 제거되고 그 자리를 `output_config.effort`가 대신하고 있었습니다.
>
> 선택지가 세 개 있었습니다. **① 옵션을 지운다** — 과제 요구를 안 지키는 겁니다.
> **② 그대로 보낸다** — 사용자가 쓰면 무조건 에러가 납니다.
> **③ 옵션은 제공하되, 받아주는 모델에만 실제로 보낸다** — 이걸 골랐습니다.
>
> 그래서 `MODELS_ACCEPTING_TEMPERATURE`라는 목록을 두고, 거기 없는 모델이면
> **보내지 않고 경고를 출력하면서 `--effort`를 안내합니다.**"

```
[WARN] --temperature 0.9 는 전송하지 않았습니다. claude-opus-5-5 은 샘플링
       파라미터를 더 이상 받지 않습니다(400). 품질은 --effort 로 조절하세요
       (현재 low). 일부러 전송해 400 을 보려면 --legacy-temperature 를 쓰세요.
```

> "그리고 **`--legacy-temperature`라는 옵션을 하나 더 뒀습니다.** 이걸 주면
> **일부러 그대로 전송해서 400 에러를 직접 보여줍니다.** 제가 '에러가 난다'고 말로만
> 하는 것보다, 평가장에서 실제로 보여드릴 수 있는 게 낫다고 생각해서 넣었습니다."

**세 파라미터의 차이** — 꼭 물어보는 부분입니다.

| 파라미터 | 조절하는 것 | 비유 |
|---|---|---|
| `temperature` | 다음 단어를 고를 때의 **무작위성** | 주사위를 얼마나 굴릴지 |
| `effort` | **얼마나 깊게 생각할지**와 토큰 예산 | 고민을 얼마나 할지 |
| `max_tokens` | **출력 길이 상한** | 답변 종이의 크기 |

> "**`max_tokens`는 품질 조절 장치가 아니라 안전장치입니다.** 올리면 답이 좋아지는 게
> 아니고, **너무 낮으면 문장 중간에서 잘립니다.** 그래서 잘렸을 때는 경고를 띄웁니다.
>
> 기본 `effort`는 **`low`** 로 뒀습니다. **diff를 요약하는 건 깊은 추론이 필요한 작업이
> 아닙니다.** 복잡한 변경이면 올리면 되는데, 그런 경우는 드뭅니다."

### ④ 읽을 말 — 예외 대응 (7가지를 따로 잡습니다)

`llm.py` 172~215줄입니다. **여기가 가장 많이 질문받을 부분입니다.**

> "예외를 **구체적인 것부터 7가지로 나눠서** 잡습니다. 하나로 뭉쳐서 `except Exception`으로
> 잡으면 **'다시 시도하면 되는 오류'와 '고쳐야 하는 오류'를 구분할 수 없습니다.**"

| 잡는 예외 | 상황 | 사용자에게 뭐라고 하나 | 성격 |
|---|---|---|---|
| `AuthenticationError` | 401 | 키가 틀렸거나 만료됐다 → 콘솔에서 확인 | **고쳐야 함** |
| `PermissionDeniedError` | 403 | 이 키에 그 모델 권한이 없다 | **고쳐야 함** |
| `NotFoundError` | 404 | 모델 이름이 틀렸다 → `--model` 확인 | **고쳐야 함** |
| `BadRequestError` | 400 | 요청이 잘못됐다 (+ temperature면 힌트 추가) | **고쳐야 함** |
| `RateLimitError` | 429 | 몇 초 뒤 다시 시도 (`retry-after` 헤더를 읽음) | **기다리면 됨** |
| `APIStatusError` 5xx | 서버 문제 | 잠시 뒤 다시 시도 | **기다리면 됨** |
| `APIConnectionError` | 네트워크 | 인터넷/프록시 확인 | **환경 문제** |

> "**429는 특별히 처리했습니다.** 응답 헤더에 `retry-after`라는 값이 들어오는데, 거기
> '몇 초 뒤에 다시 오라'는 숫자가 있습니다. 그걸 읽어서 **'60초 뒤에 다시 시도하세요'**
> 처럼 구체적으로 알려줍니다. 헤더가 없을 수도 있어서 기본값 60초를 둡니다."

**종료코드를 나눈 이유** — 실측했습니다.

```bash
env -u ANTHROPIC_API_KEY python3 main.py commit; echo $?   # → 2
cd /tmp && python3 .../main.py commit; echo $?             # → 1
python3 main.py preview; echo $?                           # → 0
```

> "종료코드를 **0(정상) / 1(git 문제) / 2(키 없음) / 3(API 실패)** 로 나눴습니다.
> **종료코드는 사람이 아니라 다른 프로그램이 읽는 값입니다.** 이 도구를 스크립트나
> CI에 넣는다면 '키가 없어서 못 했다'와 'API가 거절했다'를 구분해서 다르게 대응해야 합니다.
> 전부 1로 돌려주면 그걸 못 합니다."

### 설명하기 좋은 판단 — 키 검사를 import보다 먼저 한다

`llm.py` 155~158줄. **코드에 날짜까지 적어둔 부분입니다.**

> "`call` 함수 안에서 **키 검사를 `import anthropic`보다 먼저** 합니다.
> 순서를 바꿔봤더니, `anthropic` 패키지가 없는 환경에서 **'패키지가 없다'는 에러가 먼저
> 떠서 '키가 없다'는 안내가 묻혀버렸습니다.** 2026-11-07에 실제로 겪었고, 그때 과제
> 7쪽의 출력 예시가 재현되지 않아서 알았습니다.
>
> 사용자 입장에서는 **키를 먼저 알려주는 게 맞습니다.** 패키지는 `pip install` 한 줄이고,
> 키는 발급받아야 하는 일이라 더 오래 걸립니다."

### 설명하기 좋은 판단 — 응답을 조용히 넘기지 않는다

`llm.py` 220~234줄.

> "응답이 와도 두 가지를 확인합니다.
> **`stop_reason`이 `refusal`이면** 모델이 요청을 거절한 겁니다 — 에러로 올립니다.
> **`max_tokens`면** 출력이 길이 상한에 걸려 잘린 겁니다 — 경고하면서 옵션을 안내합니다.
>
> 이걸 확인하지 않으면 **잘린 커밋 메시지를 정상인 것처럼 보여주게 됩니다.**
>
> 그리고 응답의 `content`는 **블록 목록**입니다. 하나의 문자열이 아니라서,
> **`type`이 `text`인 블록만 골라서** 이어붙입니다. 결과가 비어 있으면 그것도 에러입니다."

## 4. 요구사항 3·4 — 커밋 메시지와 PR 초안 / 프롬프트 설계

### ① 평가자가 확인하는 것
프롬프트를 어떻게 구성했는지. **이 미션의 핵심입니다.**

### ② 실행할 명령
```bash
python3 main.py preview --for commit     # 커밋 쪽 프롬프트 전문
python3 main.py preview --for pr         # PR 쪽 프롬프트 전문
sed -n '1,20p' aigitgen/prompts.py       # 설계 원칙 4가지
```

### ③ 나올 결과
`SYSTEM PROMPT`와 `USER PROMPT (실제 전송 내용)` 두 덩어리가 구분선에 싸여 나옵니다.

### ④ 읽을 말

> "**프롬프트를 코드 안에 흩어놓지 않고 `prompts.py` 한 파일에 모았습니다.**
> 이 과제의 핵심이 '단순 API 호출'이 아니라 **어떤 입력을 주는가** 라서 그렇습니다.
> 설계 원칙을 그 파일 맨 위에 네 가지로 적어뒀습니다."

**원칙 1 — 역할과 규칙은 system, 변하는 데이터는 user**

> "`system`은 매 호출마다 같으니 **캐시가 되고**, 규칙이 긴 diff에 섞여 **희석되지 않습니다.**"

**원칙 2 — 출력 형식을 예시로 못 박는다**

> "'짧게 써라' 같은 말보다 **원하는 모양을 그대로 보여주는 쪽이 훨씬 잘 지켜집니다.**
> 그래서 `system` 프롬프트 끝에 **출력 예시를 통째로** 넣었습니다."

**원칙 3 — 모르는 건 지어내지 말라고 명시한다**

> "**이 도구의 가장 큰 위험은 diff에 없는 내용을 그럴듯하게 쓰는 것입니다.**
> 커밋 메시지는 나중에 '왜 이걸 고쳤나'를 찾는 기록인데, 거기 추측이 섞이면
> **기록이 거짓이 됩니다.** 그래서 규칙에 세 번 반복해 넣었습니다 —
> 'diff에 없는 내용은 쓰지 않는다', '의도나 배경을 추측하지 않는다',
> '없는 명령어를 만들지 않는다'."

PR 쪽에는 한 줄 더 넣었습니다.

> "PR의 `## Why`는 '왜 이 변경이 필요했나'인데, **배경은 diff에 안 적혀 있습니다.**
> 그래서 **'모르면 「diff 상으로는 ~를 위한 변경으로 보입니다」처럼 근거를 밝혀라'**
> 라고 지시했습니다. 모르는 걸 모른다고 쓰게 만드는 게 지어내게 하는 것보다 낫습니다."

**원칙 4 — 재생성 때는 무엇이 틀렸는지 되돌려준다** (뒤 5절에서 자세히)

### 설명하기 좋은 판단 — 파일 목록을 diff 앞에 따로 넣는다

`prompts.py` `_changes_block` 함수입니다.

> "프롬프트에 **① 변경 범위 ② 변경된 파일 목록 ③ `git status` 원문 ④ `git diff`**
> 순서로 넣습니다. **파일 목록을 diff 앞에 따로 두는 게 의도적입니다.**
>
> diff가 길면 모델이 **앞부분에 더 집중합니다.** '무엇이 바뀌었나'의 요약을 먼저 주면
> 뒤쪽 파일을 놓치지 않습니다. diff만 던지면 **마지막 파일이 요약에서 빠지기 쉽습니다.**"

### 커밋 메시지 규칙 (`COMMIT_SYSTEM`)

> "제목은 **`<type>: <요약>`** 형식이고 type은 feat, fix, docs, refactor, test, chore,
> perf, style 중에서 고르게 했습니다. **50자 목표, 72자 절대 상한**입니다.
> 본문은 `- ` 불릿 1~3개이고, **변경된 파일이나 모듈 이름을 최소 1개 언급**하게 했습니다.
>
> 파일 이름을 강제한 이유는, **그게 없으면 '기능 개선'처럼 아무 정보 없는 본문이**
> 나오기 때문입니다. 파일 이름이 들어가면 최소한 '어디를 봐야 하는지'는 알 수 있습니다."

### PR 규칙 (`PR_SYSTEM`)

> "본문에 **`## Why` / `## What` / `## How to Test`** 세 섹션을 **이 순서로, 이 글자
> 그대로** 넣게 했습니다. 각 섹션에 불릿이 최소 1개 있어야 합니다.
>
> **`## How to Test`에는 '실제로 저장소에 있는 명령만 적어라'** 고 지시했습니다.
> 없는 테스트 명령을 적으면 리뷰어가 그걸 돌려보고 실패합니다. **그게 PR 설명에서
> 제일 민망한 거짓입니다.**"

## 5. 요구사항 5 — 출력 형식 검증 + 구획

### ① 평가자가 확인하는 것
생성 결과가 형식 규칙을 지키는지 검증하고, 안 지키면 어떻게 하는지.
그리고 최종 출력이 **구분선/헤더로 구획**되어 있는지.

### ② 실행할 명령
```bash
python3 -m pytest tests/ -q                 # 42 passed
sed -n '1,20p' aigitgen/validate.py         # 검증 전략
sed -n '1,12p' aigitgen/render.py           # 왜 색을 안 썼나
```

### ③ 나올 결과
```
42 passed in 0.04s
```

### ④ 읽을 말 — 검증과 재생성 (3단 구조)

> "과제는 **'검증 후 재생성 또는 후처리 중 택 1'** 을 허용합니다.
> 저는 **둘 다** 썼습니다. 다만 **순서와 횟수에 제한**을 뒀습니다."

```
1회차 호출 → 검증 → 통과하면 끝                              (API 1회)
                  → 실패하면 '무엇이 틀렸는지' 알려주고 1회만 재생성  (API 2회)
2회차 결과 → 검증 → 그래도 실패하면 돈이 안 드는 후처리로 규칙을 강제
```

> "**왜 재생성을 한 번만 하나요?** 제약 사항에 '1회 실행 시 요청 횟수는 1~2회 이내'가
> 있습니다. **재생성을 무한히 돌리면 그 제약을 깨고, 비용이 통제되지 않습니다.**
> 그래서 재생성은 딱 한 번이고, 그 다음은 **돈이 안 드는 후처리**로 마무리합니다.
>
> **왜 재생성을 먼저 하고 후처리를 나중에 하나요?** **후처리가 결과적으로 더 나쁘기**
> 때문입니다. 제목을 기계적으로 72자에서 자르면 문장이 어색해집니다. AI가 다시 쓰면
> 자연스러운 문장이 나옵니다. **좋은 쪽을 먼저 시도하고, 안 되면 확실한 쪽으로 떨어집니다.**"

### ④ 읽을 말 — 재생성 프롬프트 (원칙 4)

`prompts.py` `retry_user` 함수입니다.

> "재생성할 때 **원래 요청을 다시 보냅니다.** 왜냐면 **API는 상태를 기억하지 않습니다.**
> 변경 사항을 빼고 '다시 써라'만 보내면 **모델이 무엇을 대상으로 쓰는지 모릅니다.**
>
> 거기에 두 개를 더 붙입니다. **① 직전 출력(틀린 결과)과 ② 위반 내용**입니다.
> 같은 요청을 그대로 다시 보내면 **같은 결과가 나옵니다.** '제목이 85자입니다, 72자
> 이내로 줄이세요'처럼 **구체적으로 알려줘야** 고쳐집니다."

### ④ 읽을 말 — 검증 항목 (오류 vs 경고를 나눴습니다)

| 검사 | 기준 | 오류/경고 |
|---|---|---|
| 커밋 제목 있음 | 비어 있으면 안 됨 | **오류** |
| 커밋 제목 길이 | 72자 초과 | **오류** |
| 커밋 제목 길이 | 50자 초과 | **경고** |
| 커밋 본문 품질 | 본문이 있으면 불릿 최소 1개 | **오류** |
| PR 제목 | 있음 / 80자 이내 / 1줄 | **오류** |
| PR 섹션 | Why·What·How to Test 헤더 존재 | **오류** |
| PR 불릿 | 각 섹션에 불릿 최소 1개 | **오류** |

> "**50자와 72자를 다르게 처리한 게 의도적입니다.** 과제가 50자를 **권장**,
> 72자를 **최대**로 구분했습니다. 그래서 **50자 초과는 경고만 하고 재생성하지 않습니다.**
> 권장치를 넘긴 것만으로 API를 한 번 더 부르면 **돈을 쓸 이유가 없는 곳에 쓰는 겁니다.**
>
> 본문은 **선택**입니다. 없어도 통과입니다. 다만 **있으면** 불릿이 있어야 합니다.
> 산문으로 길게 쓴 본문은 나중에 아무도 안 읽습니다."

### ④ 읽을 말 — 후처리는 지어내지 않는다

`validate.py` `postprocess_pr` 함수입니다. **설명하기 좋은 부분입니다.**

> "후처리에서 **비어 있는 섹션을 지어내지 않습니다.** `- (직접 채워주세요)` 라고
> 자리표시만 남깁니다. 제목이 아예 비면 `chore: (제목을 직접 작성해주세요)` 를 넣습니다.
>
> **AI가 모르는 내용을 그럴듯하게 써 넣는 게 빈칸보다 위험합니다.** 빈칸은 사람이
> 보고 채우는데, 그럴듯한 거짓말은 그냥 커밋됩니다."

> "제목을 자를 때도 **단어 경계에서** 자릅니다. 글자 중간에서 끊으면 더 이상해집니다.
> `rsplit(' ', 1)`로 마지막 공백까지 자르고, 끝에 남은 쉼표나 마침표를 떼어냅니다."

**그리고 이 함수에는 보장이 하나 걸려 있습니다.**

> "**후처리를 거친 결과는 반드시 검증을 통과해야 합니다.** 그게 후처리의 존재 이유입니다.
> 통과하지 못하면 3단 구조의 마지막 단이 무의미해집니다.
> **이 보장이 깨지는 걸 테스트가 잡아냈습니다** — 뒤 8절에 적어뒀습니다."

### ④ 읽을 말 — 출력 구획 (`render.py`)

> "과제가 '최종 출력은 구분선/헤더 등으로 구획이 나뉘어 표시되어야 한다'고 요구합니다.
> `render.py`가 그걸 합니다. **72자 너비**로 `--- Commit Message ---...` 같은 구분선을
> 만들고, 호출 정보는 `===` 로 감쌉니다.
>
> **색은 일부러 안 썼습니다.** 터미널 색은 이스케이프 문자로 들어가는데,
> **로그를 복사해서 리포트에 붙이면 그 문자가 그대로 따라옵니다.** 제출물에
> `\033[31m` 같은 게 섞이면 읽을 수 없게 됩니다."

> "그리고 **오류만 표준에러(`stderr`)로 보냅니다.** 나머지는 표준출력입니다.
> 결과를 파이프로 다른 프로그램에 넘길 때 **에러 메시지가 결과물에 섞이지 않게** 하려는 겁니다."

**여기서 재미있는 걸 하나 발견했습니다** — 평가장에서 보일 수 있으니 미리 알아두세요.

> "출력을 `2>&1 | head` 처럼 파이프로 넘기면 **`[ERROR]`가 `[INFO]`보다 먼저 나옵니다.**
> 순서가 뒤바뀐 것처럼 보이는데, 버그가 아닙니다. **`stderr`는 버퍼링이 없어 바로 나가고,
> `stdout`은 파이프로 넘길 때 버퍼에 모아뒀다가 한꺼번에 나가기** 때문입니다.
> 터미널에 직접 출력하면 순서대로 나옵니다."

## 6. safe-mode — 민감정보 (가장 강한 시연)

### ① 평가자가 확인하는 것
`git diff`에 민감정보가 들어갈 수 있다는 걸 인지하고 대응했는지.

과제 제약은 **아래 둘 중 하나 이상**을 요구합니다. **둘 다 했습니다.**
- (A) 특정 패턴(API Key 형태, 이메일 등)을 마스킹 후 전송
- (B) diff 일부만 전송 (예: 최대 10개 파일, 최대 200줄)

### ② 실행할 명령
```bash
# 0절에서 만든 가짜 키가 들어간 변경이 staged 되어 있어야 합니다
python3 main.py preview | grep -E 'MASKED|마스킹'

python3 main.py preview --max-lines 5 | grep -E 'WARN|잘렸'
python3 main.py preview --no-safe-mode | grep WARN
```

### ③ 나올 결과 — **제가 실측한 값입니다**

```
[INFO] 민감정보 마스킹: 총 1건 (anthropic_key 1건)
+DEMO_KEY = "sk-ant-***MASKED***"
```
```
[WARN] diff 가 잘렸습니다: 1개 파일 / 11줄 중 1개 파일 / 7줄만 전송 (--max-files, --max-lines 로 조절)
[... diff 가 safe-mode 제한으로 잘렸습니다 (최대 10개 파일 / 5줄) ...]
```
```
[WARN] safe-mode 가 꺼져 있습니다. diff 가 손대지 않은 상태로 전송됩니다.
```

### ④ 읽을 말

> "**`git diff`에는 비밀값이 들어 있을 수 있습니다.** `.env` 파일 수정, 하드코딩된 키,
> 테스트용 개인정보가 그대로 담깁니다. 그걸 외부 API로 보내면 **되돌릴 수 없습니다.**
> **요청은 취소할 수 있어도 이미 전송된 데이터는 지울 수 없습니다.**
>
> 그래서 **safe-mode가 기본으로 켜져 있습니다.** 끄려면 `--no-safe-mode`를 **명시적으로**
> 줘야 하고, 끄면 경고가 나옵니다. **안전한 쪽이 기본값이어야 합니다** — 사용자가
> 모르고 켜는 일은 없어야 하지만, 모르고 끄는 일도 없어야 합니다."

**마스킹하는 패턴 9종** (`sanitize.py`의 `MASK_RULES`)

| 종류 | 예 |
|---|---|
| Anthropic / OpenAI 키 | `sk-ant-...`, `sk-...` |
| AWS | `AKIA...`, `aws_secret_access_key=...` |
| GitHub 토큰 | `ghp_...`, `gho_...` |
| `KEY=VALUE` 꼴 | `DB_PASSWORD="..."`, `API_KEY=...` |
| Bearer 토큰 | `Authorization: Bearer ...` |
| 이메일 / 휴대폰 / 주민번호 꼴 | — |
| 사설 키 블록 | `-----BEGIN ... PRIVATE KEY-----` |

### ④ 읽을 말 — 순서가 두 번 중요합니다

**(1) 마스킹 → 제한 순서**

> "**마스킹을 먼저 하고 그 다음에 자릅니다.** 순서를 바꾸면 안 됩니다.
> **먼저 자르면, 잘려나간 부분의 비밀값은 검사조차 되지 않습니다.**
> 마스킹을 먼저 해야 **'보낸 것 중에 비밀값이 없다'를 보장**할 수 있습니다."

**(2) 패턴 목록 안의 순서**

> "`MASK_RULES` **목록 안의 순서도 중요합니다. 더 구체적인 패턴을 먼저 둬야 합니다.**
> 예를 들어 이메일을 먼저 지우면 `user@example.com` 안의 도메인이 사라져서,
> 뒤에 오는 패턴이 엉뚱한 걸 잡습니다."

### ④ 읽을 말 — 파일 경계를 지켜서 자른다

> "전송량 제한은 **파일 경계를 지켜서** 자릅니다. `git diff`는 파일마다
> `diff --git a/... b/...` 로 시작하니까 그 줄을 경계로 씁니다.
>
> **줄 수만 보고 자르면 diff가 중간에서 끊겨 AI가 변경 내용을 오해합니다.**
> 함수 절반만 보고 '함수를 삭제했다'고 쓸 수 있습니다. **덩어리째 버리는 게 낫습니다.**
> 그리고 잘렸다는 사실을 **diff 안에 명시적으로 적어** 보냅니다 — 모델이
> '여기까지가 전부'라고 오해하지 않게요."

### ④ 읽을 말 — 한계를 솔직하게 (여기가 가장 인상적인 부분입니다)

> "**정규식은 '그렇게 생긴 것'만 잡습니다. 완벽한 탐지는 불가능합니다.**
> 그래서 README에 'safe-mode는 보조 장치이고 최종 책임은 사용자'라고 적었습니다.
>
> 실제로 함정에 빠진 적이 있습니다. 처음에 `KEY=VALUE` 규칙의 값 부분을
> `[^\s\"']{4,}` 로 **느슨하게** 잡았습니다. 그랬더니
> **`api_key = resolve_api_key()` 같은 평범한 코드까지 마스킹해 버렸습니다.**
> 제 소스코드 diff에서 **3건이 오탐**으로 걸렸습니다.
>
> **비밀값이 아닌 걸 가리면 AI가 실제 코드를 못 보고 요약 품질이 떨어집니다.**
> 안전한 쪽으로 실수하는 것도 **공짜가 아니라는 걸** 그때 알았습니다.
>
> 고친 방법은 규칙을 **둘로 쪼갠 것**입니다. **① 따옴표로 감싼 리터럴**과
> **② 토큰 끝까지 이어지는 맨 값**만 잡습니다. 함수 호출은 값 뒤에 `(` 가 오니까
> **끝 앵커 `(?=[\s;,]|$)`에서 걸러집니다.** 그리고 **오탐 회귀 테스트**를 넣어서
> 다시 느슨해지지 않게 막았습니다."

> "그리고 결론은 이렇습니다. **보낼 내용을 미리 확인하는 습관이 가장 확실합니다.**
> 그래서 `preview` 명령을 만들었습니다 — **돈을 쓰지 않고 전송될 내용 전체를 보여줍니다.**"

## 8. 제약 사항 — 하나씩 어떻게 지켰나

## 9. 테스트 — 그리고 테스트가 실제로 잡은 버그 4개

**이 절이 평가표의 「경험 정도 / 재구현 가능 여부」 칸에 가장 도움이 됩니다.**

> "`preview` 명령이 **커밋 프롬프트를 못 보여주고 항상 PR 쪽으로 떨어졌습니다.**

## 10. 꼬리 질문 모음 — 예상되는 것들

**Q. AI가 틀린 커밋 메시지를 쓰면요?**
> "그게 이 도구의 가장 큰 위험이라고 보고 **세 겹으로 막았습니다.**
> ① 프롬프트에서 '**diff에 없는 내용은 쓰지 마라**'를 세 번 반복합니다.
> ② 본문에 **파일 이름을 최소 1개 언급**하게 해서, 최소한 어디를 봐야 하는지는 맞게 합니다.
> ③ 그래도 **자동으로 커밋하지 않습니다.** 마지막 줄에 '검토 후 적용하세요'를 출력하고
> 끝납니다. **최종 판단은 사람이 합니다.**"

**Q. 왜 Claude를 썼나요? 다른 API는요?**
> "과제 예시가 `AI_API_KEY`라는 변수명을 쓰는데, 특정 회사를 지정하진 않았습니다.
> Claude를 고른 건 **제가 쓸 수 있는 키가 있었기 때문**입니다.
> 다른 API로 바꾸려면 **`llm.py` 한 파일만** 고치면 됩니다 — 요청 조립과 예외 처리가
> 거기 모여 있고, `prompts.py`나 `validate.py`는 특정 회사에 묶여 있지 않습니다."

**Q. `effort`가 뭔가요? 처음 듣습니다.**
> "**모델이 답하기 전에 얼마나 깊게 생각할지**를 정하는 값입니다. `low`에서 `max`까지
> 있습니다. 예전에는 `temperature`로 품질을 조절했는데, 최신 모델에서 그게 빠지고
> 이게 들어왔습니다. **낮으면 빠르고 싸고, 높으면 느리고 비싸지만 복잡한 변경을 더
> 잘 요약합니다.** 기본은 `low`입니다 — diff 요약에 깊은 추론은 필요 없습니다."

**Q. `--convention`은 왜 만들었나요?**
> "**커밋 prefix 규칙이나 PR 템플릿이 팀마다 다릅니다.** 코드에 박아두면 다른 팀에서
> 못 씁니다. 파일로 적어두고 넘기면 **프롬프트 맨 뒤에 '팀 컨벤션 (반드시 따른다)'으로
> 붙습니다.** 파일이 없으면 경고만 하고 그냥 진행합니다 — **없는 파일 때문에 도구가
> 멈추면 안 됩니다.**"

**Q. diff가 아주 크면요?**
> "기본 **10개 파일 / 200줄**에서 잘립니다. 그 이상은 `--max-files`, `--max-lines`로
> 올릴 수 있지만, **권하지 않습니다.** 입력 토큰이 비용의 대부분이고, 무엇보다
> **변경이 200줄을 넘으면 커밋을 쪼개는 게 맞습니다.** 한 커밋에 여러 성격의 변경이
> 섞이면 메시지도 뭉개집니다."

**Q. `git status`를 왜 보내나요? diff만 있으면 되지 않나요?**
> "`git diff`는 **내용의 변화**만 보여주고, `git status`는 **파일의 상태**를 보여줍니다.
> 새 파일인지, 이름이 바뀐 건지, 삭제된 건지는 `status`에 나옵니다.
> 둘을 같이 보내야 **'무엇이 어떻게 바뀌었나'가 완성됩니다.**"

**Q. 혼자 만들었나요?**
> *(정직하게 답하시는 게 맞습니다. AI 도구를 쓴 미션이니 AI를 쓴 것 자체는 문제가
> 아닙니다. 다만 "제가 이해하고 설명할 수 있다"가 증명되어야 합니다. 이 문서의
> 9절에 있는 버그 4개가 그 증거입니다 — 실제로 막혀서 고친 것들입니다.)*
